## 4. Owner

Derivation owner (INF, from 2b): the single accessor every reader funnels through, `SystemConfig::get_connectionMode()` (declared src/persist/SystemConfig.h:157, defined src/MyPersistentData.cpp:1050). Make it return effective = configured, except INTERMITTENT when `lowBatteryMode` is set, stored==KEEP_ALIVE and sensorMode==OCCUPANCY (same condition BatteryAuthorityCommand.cpp:76-80 uses). Add one raw getter for the configured value. All ~30 reader call sites then need no change. (A policy-layer function would instead require editing every reader, about 30 lines of churn.)

More than one owner? YES (INF, judgement call). The derivation lives in one place, but the fix cannot work unless two other owners also change:
1. src/power/BatteryAuthorityCommand.cpp (downgrade owner): delete the two writes at :83 and :90; read the configured getter at :77. The flag then alone represents the downgrade.
2. src/cloud/ConfigApply.cpp (config owner): compare against the configured getter at :448; the `|| lowBatteryMode` clause and the :455 clear are no longer needed.
3. src/MyPersistentData.cpp + src/persist/SystemConfig.h (store/accessor owner): effective derivation and configured getter.
So three files, three owners. If Chip counts only "who derives effective", the answer is one; counting who must change, it is more than one.

Estimate (INF, not a design): accessor change and configured getter in MyPersistentData.cpp about +10; declaration +1; BatteryAuthorityCommand.cpp -2 writes, +1 getter swap, maybe +2 comment/log; ConfigApply.cpp about -4 to -6 (drop clause and clear) +1. Net roughly +8 to +20. Reasoning: mostly deletions elsewhere plus one small derived accessor. Upper end allows a Log.info on downgrade-effective changes. Within the +15 to +35 budget at the high end, and likely at or below its floor. Risks that could push it up: (a) devices already holding an overwritten INTERMITTENT with the flag set lose the configured value; the first ConfigApply (it fires because the flag is set, :449) rewrites it from the ledger, so it self-heals, but a test is needed; (b) stale flag when sensorMode leaves OCCUPANCY; handled by the OCCUPANCY term; (c) the config-hash input (DeviceStatusPublisher.cpp:113) should use the configured getter or the hash will change at every downgrade.

## 5. Bench plan for Chip (Dev-14, BRN404X, Singtel)

Preconditions (ledger edits Chip can make): `modes.sensorMode` = OCCUPANCY and `modes.connectionMode` = 3 (INTERMITTENT_KEEP_ALIVE), because the downgrade only fires in that combination (BatteryAuthorityCommand.cpp:76, :80). Tier is a pure function of battery SoC (src/cloud/BatteryBackoffPolicy.h:24-39: HEALTHY at >=75 %, drops to CONSERVING below 70 % unless already CONSERVING, below 75 % when it had left HEALTHY), additionally guarded by the vcell/trust checks in BatteryAuthority::evaluate. The firmware offers no knob that forces a tier, so the trigger is physical: run Dev-14 on a battery whose SoC is under 70 % (let it discharge or swap in a partly charged pack), and recover by charging above 75 %. If the pack cannot be brought below 70 % without new code, there is no firmware-only trigger; I am not proposing code. Expected serial/log lines: (i) downgrade: `Battery tier transition: HEALTHY -> CONSERVING (SoC=..)` (BatteryAuthorityCommand.cpp:63) followed by `Battery conservation: Disabling KEEP_ALIVE mode ... switching to INTERMITTENT` (:81); report/status field `battery.tier` = CONSERVING and `battery.lowBatteryMode` = true (DeviceStatusPublisher.cpp:254-255). (iii) recovery: `Battery tier transition: ... -> HEALTHY`, then `Battery recovery: clearing lowBatteryMode (tier=HEALTHY...)` and `Battery recovery: restoring INTERMITTENT_KEEP_ALIVE ...` (:86, :88), `battery.lowBatteryMode` false. After the fix the restore line is expected only as a flag-clear. Dev-14 note: weak Singtel coverage means stale cloud with a healthy serial is normal, so judge from serial, not the cloud.

## 8. Migration check (Claude Code, 2026-10-07, base 41ad238)

Question: when does config apply run? It runs on every successful cloud connection, so the check **passes**.

- **Every connect:** `Cloud::loadConfigurationFromCloud()` (cloud/Cloud.cpp:634-645) is called on the connect-success path in State_Connect.cpp:561, after `CLOUD_CONNECTED` (:510). No generation or "changed" gate sits in front of it: `applyConfigurationFromLedger` (cloud/ConfigApply.cpp:123-180) always runs every section.
- **Ledger sync:** LedgerClient.cpp:55 and :67 set `pendingConfigApply`, and `Cloud::loop()` (cloud/Cloud.cpp:678-690) applies it while connected.
- **OTA connect:** State_Connect.cpp:718 runs it once in FIRMWARE_UPDATE_STATE.
- **Not at boot:** there is no call in `setup()`.

Effect on a device that is downgraded when the OTA arrives (stored mode 1, `lowBatteryMode` true): from boot until its first connect, the stored INTERMITTENT acts as the configured mode, which is what the device already does today. At the first connect, `applyModesConfig` compares ledger 3 with configured 1 and writes 3. From then on, the mode in use comes from PowerManager's derivation. Chip still checks fleet device-status for `battery.lowBatteryMode: true` before rollout.
