## Q5: PROCEED
All six WOs are behavior-neutral, need no new persisted field, and each is ≤ +20 net. The total is ≈ +57 net `src/` plus 6b–6d's ≈ −45 (outside the +20 each).

**Cut or defer from the WO's wish list:**
- (iv) *Settings from `setting1–4` and `samplingMode` as the reading mode.* They are already read from the store, `samplingMode` is unused at runtime, and wiring it would change behavior for any device with ledger `samplingMode=1`, which this session cannot see. Defer to the first non-interrupt sensor.
- *"Ask for a report"* as an `ISensor` method. Triggers are mode-handler logic with no second consumer. Defer.

## Open points
1. **Golden-test approach:** extract-verbatim (2b-1) versus waiting for 2b-2. Recommend 2b-1 first, so the move in 2b-2 is proved against a fixture written before the code changed.
2. **`alerts`/`resets` order** differs by mode (rows 7–8). Byte-identical forbids fixing it; architect to say if it should stay.
3. **MEASUREMENT mode (2)** publishes the counting format. Pin it as is.
4. **`temp` is unguarded** against NaN/Inf, unlike `battery` (`:1994–1998`). Out of scope, but 2b-1 should record the current behavior.
5. **`SensorFactory` only knows PIR;** `sensor.type` is validated 1..1 (`ConfigApply.cpp:352`), so a second sensor also needs that range widened (a persisted-value validation change, not a new field).
6. **`hasFuelGauge` and the labels are power code.** Confirm they stay in 2b-6 or move to a power WO.
