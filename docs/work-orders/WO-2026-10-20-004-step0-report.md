## 2. Car counters

Observation: VC uses `SCK`, `INPUT_PULLDOWN`, and `RISING`; `MOSI` enables the module and `MISO` drives its LED: VC `Visitation-Counters.ino:205–207,251–253,370–372` (at `377cfd3`). For pressure type 0, a RAM `frontTireFlag` discards the first rising edge and counts the second; there is no timer, minimum gap, or debounce: VC `Visitation-Counters.ino:974–982` (at `377cfd3`). Pressure LED power is active-high, versus active-low for PIR: VC `Visitation-Counters.ino:694–715` (at `377cfd3`).

GCC already reserves stable `sensor.type=0` for pressure and records the correct LED polarity, but its factory implements only type 1 and ledger validation rejects 0: GCC `SensorFactory.h:13–50,71–88`, GCC `SensorDefinitions.h:23–33`, and GCC `ConfigApply.cpp:332–408` (at `a3e012d`). That restriction came from `96c984c` (“sensor.type from the ledgers reaches sensor creation”), when PIR was the only implementation.

Recommendation: use **distinct `sensor.type=0` sharing the existing interrupt sensor machinery**, not a disguised PIR setting. This preserves the established external type identity while adding only polarity and “every second rising edge” policy. The policy must cover both awake detections and GCC’s synthesized wake count, which currently increments directly: GCC `State_Sleep.cpp:1524–1543` (at `a3e012d`). Its pairing state may remain RAM, matching VC; no persisted field is required.

The deferred 2b-8a/8b work becomes due here if the common sensor is to receive `setting1–4` and `samplingMode`; their accepted estimates are +19 and +12: GCC `WO-2026-10-13-002-step0-round2-report.md:59–61` (at `a3e012d`). Exact v50 equivalence needs neither a configurable gap nor debounce, so use settings only for an explicit future policy. 2b-7’s +17 report request is not behaviorally needed for scheduled counters and can remain deferred: GCC `WO-2026-10-13-002-step0-round2-report.md:55–57` (at `a3e012d`).

## 3. Payload

VC order and formats are: integer `hourly,daily,battery`, string `key1`, integer `temp,resets,alerts,maxmin,connecttime`, then `timestamp`; event `Ubidots-Counter-Hook-v1`, `PRIVATE|WITH_ACK`: VC `Visitation-Counters.ino:771–784` (at `377cfd3`). Its nonzero timestamp is the most recent count; otherwise it is the previous report time.

GCC COUNTING order is `hourly,daily`, two-decimal `battery`, two-decimal `vc`, `key1`, two-decimal `temp`, `resets,alerts,connecttime,fh,lfb,cyc,slp,timestamp`; event name comes from the ledger: GCC `ReportPublisher.cpp:59–65,95–124` (at `a3e012d`). The committed golden demonstrates the exact bytes and `my-hook`: GCC `tests/fixtures/report_payload_golden.txt:1–4` (at `a3e012d`). GCC drops `maxmin`, adds diagnostics, and timestamps the end of the previous interval.

Fleet Operations accepts unknown event types, preserves raw events, and normalizes additively: FleetOps `architecture.md:270–281` (at `401414f`). Its documented generic parser handles `temp`/`temperature`: FleetOps `tools.md:826–830` (at `401414f`). However, its architecture names only `Ubidots-Sensor-Hook-v1`, not the legacy counter hook: FleetOps `architecture.md:17–20` (at `401414f`).

Therefore the fleet tools can ingest/archive the event, but **the trees cannot establish what the Particle webhook template, Ubidots variables, dashboards, or alerts require**.
