## Pre-dispatch findings (Claude Code, read-only, 2026-09-29)

### A: the connect decision

`handleReportingState()` computes `due` (the daily boundary is due, on a trusted clock) near the top, then decides whether to connect. The triggers are: service request, occupancy change, long-term webhook health, `INTERMITTENT_KEEP_ALIVE` mode (connect for every report), and `reportingPolicy.cadenceDue` (aligned). Otherwise it goes to `IDLE_STATE` ("not aligned"). A device that the battery policy has moved out of keep-alive mode (for example "Battery conservation: Disabling KEEP_ALIVE mode ... switching to INTERMITTENT", seen on the Dev-14 bench) therefore holds its 22:00 closing report until the next aligned slot, which is the morning.

### B: history of the broad subscription

`git log -S "hook-response/"`: the subscription was added in **`eda6b7e` (v3.24, 2026-02-09)**, the same commit that dropped `WITH_ACK` (WO-2026-09-25-001). The stated reason: "Also subscribe to the default Particle webhook response prefix so this works with whatever webhook name is configured in the ledger. If the integration uses the default response topic, responses will be published to: hook-response/<eventName>." The original response topic (`8aa2643`) was the device ID alone.

**Does anything depend on it? No.** The product's integrations (product 42131, read-only via the Particle API) all reply on `{{PARTICLE_DEVICE_ID}}/hook-response/{{PARTICLE_EVENT_NAME}}`: both `Ubidots-Sensor-Hook-v1` integrations (Ubidots and the AWS ingest copy), `Ubidots-Counter-Hook-v1`, both `Ubidots_Alert_Hook`s, `status`, `watchdog`, `hibernate_wake`. Subscriptions match by prefix, so `"hook-response/"` never matches those. **The only reply it catches is `pdiag`'s**, whose integration has no response topic and so replies on Particle's default `hook-response/pdiag/...`. That reply clearing the report wait is the WO-2026-09-25-002 problem. With v26, release builds don't publish `pdiag`, so the subscription is inert as well as unneeded. Nothing in `src/` or `tests/` refers to it except the subscribe call.

**Remaining gap, not in this WO (Chip, 2026-09-29: implement B as specified, file the rest):** the device-ID subscription also receives the replies for `status`, `watchdog`, `hibernate_wake`, and the AWS-ingest copy of `Ubidots-Sensor-Hook-v1`, and `UbidotsHandler()` clears the wait on any of them. Recorded in WO-2026-09-25-002.

### C: the saved guard

On `archive/wo-2026-09-25-001-round3`, `src/cloud/DeviceStatusPublisher.cpp`:

```cpp
if (writerBase.dataSize() >= sizeof(bufferBase)) {
    Log.error("LedgerPayloadStatus: overflow bytes=%lu/%lu schema=%d - status not published",
              (unsigned long)writerBase.dataSize(),
              (unsigned long)DEVICE_STATUS_PAYLOAD_CAPACITY,
              kLedgerSchemaVersion);
    return false;
}
```

It sits immediately before `bufferBase[writerBase.dataSize()] = '\0';`. `JSONBufferWriter::dataSize()` "can be greater than buffer size" (Device OS 6.4.1 `spark_wiring_json.h:232`): the writer stops copying but keeps counting, so without the guard the NUL store indexes past the stack buffer. The archived version carried an 8-line comment; to fit the budget, reapply the 7 code lines with at most a one-line comment. The archive's separate "counters not emitted here" comment is not part of this item.

### D: where `local=` comes from

`logTimeDiag()` reads `LocalTimeCache::getLocalTimeSnapshot()`, which refreshes once per UTC minute, so `local=` lags `utc=` by up to 59 s (the cosmetic issue traced 2026-09-27). `State_Report.cpp`'s `localTodayAt()` already shows the live pattern: `LocalTimeConvert converter; converter.withConfig(LocalTime::instance().getConfig()).withCurrentTime().convert();`, then `getLocalTimeYMD()` and `getLocalTimeHMS()` (`LocalTimeHMS::toSeconds()` exists). The minute/second derivation lines stay.
