**OBSERVATION:** The two application deep-power-down sites are Error resolution 3 and failsafe stage 3 (`src/state/State_Error.cpp:163-170`; `src/power/ConnectivityFailsafe.cpp:310-314`).

**OBSERVATION:** `AB1805::deepPowerDown()` contains an eighth, bare library `System.reset()` fallback after waiting the requested power-off interval (`lib/AB1805_RK/src/AB1805_RK.cpp:496-506,575-592`).

**OBSERVATION:** The internal 60-second Device OS watchdog is initialized and started in setup; expiry records only a retained breadcrumb before hardware reset (`src/Generalized-Core-Counter.cpp:416-463`; `src/observability/LoopForensics.cpp:390-393`). The external AB1805 watchdog is armed for 124 seconds and serviced from the application loop (`src/Generalized-Core-Counter.cpp:778-800,1163-1166`).

**OBSERVATION:** No `System.dfu()`, NVIC reset, or equivalent explicit DFU/reset call exists in application `src/`. OTA progress is only recorded by a system-event handler (`src/Generalized-Core-Counter.cpp:130-137,1484-1489`).

**OBSERVATION:** Reset-like sleep entries are boot-storm ULP (`src/Generalized-Core-Counter.cpp:387-397`) and nightly HIBERNATE (`src/state/State_Sleep.cpp:689-743`). Ordinary ULP and STOP return in the same execution (`src/state/State_Sleep.cpp:760-925`); successful HIBERNATE reboots, while a returned call is treated as failure.

**INFERENCE:** Hardware-watchdog expiry and successful HIBERNATE are not routable reset requests: execution has either hung already or entered Device OS sleep. They must remain explicit exceptions to “Error is the only reset owner.”

## 3. Can each site route through the owner?

**INFERENCE:** OOM, ThrashGuard, nightly heap guard, sleep-exhaustion and failsafe run from the application loop and can request Error ownership using a fixed-size, allocation-free API such as `requestReset(ResetCause, ResetAction, deadlineMs)`. The request must preserve the first/highest-priority cause and transition immediately to `ERROR_STATE`.

**OBSERVATION:** OOM handling was deliberately restored from Error routing to immediate reset in commit `1c74ac8`; the test requires no Error transition and no reset-count suppression (`tests/oom_immediate_reset_test.sh:11-21,161-185,205-225`).

**INFERENCE:** OOM may route only if the new request path allocates nothing, applies no alert-based suppression, and gives OOM an immediate teardown deadline. Existing queued publishing allocates an event with `new`, so the warning step cannot be mandatory under OOM (`lib/PublishQueuePosixRK/src/PublishQueuePosixRK.cpp:69-92,98-118`).

**INFERENCE:** Thrash tier 3 can route safely, but the request must override Error’s existing “alert 18: no action” policy (`src/state/State_Error.cpp:102-106`).

**OBSERVATION:** Failsafe already defers during firmware update and persists its stage before resetting (`src/power/ConnectivityFailsafe.cpp:182-187,301-314`). Routing must preserve that order and must not let Error’s low-power alert suppression cancel the request.

**INFERENCE:** The software ApplicationWatchdog callback cannot become request-only: if the main loop is hung, it will never service the request. It and both hardware watchdogs require a documented backstop exception.

**OBSERVATION:** Vendored `deepPowerDown()` resets internally if power-off fails (`lib/AB1805_RK/src/AB1805_RK.cpp:582-592`). Therefore Error cannot literally be the sole reset caller until that fallback is removed or the native `POWER_OFF` path replaces it.

## 4. Nightly hibernate path

**OBSERVATION:** Sleep first waits for Q/ledgers/OTA/webhook, with a queue-aware 30–120 s ceiling; on timeout it raises one alert and proceeds (`src/state/State_Sleep.cpp:134-172,231-290`). It then requests cloud disconnect and modem-off and waits within configured 5–120 s limits (`src/state/SleepTeardown.cpp:149-224`; `src/power/ConnectivityPolicy.h:187-199`).

**OBSERVATION:** Every waiting pass returns to the main loop, which deferred-flushes C/S/N and services Q (`src/Generalized-Core-Counter.cpp:1168-1185`). This commonly gives the 100/250 ms delays time to expire but is not a synchronous barrier.

**OBSERVATION:** Final HIBERNATE order is: stop AB1805/internal watchdogs → arm retained hibernate state → log → optional diagnostic batch → `System.sleep(HIBERNATE)`. There is no store `flush(true)`, `writeQueueToFiles()`, or deliberate persistence delay (`src/state/State_Sleep.cpp:708-736`).

**OBSERVATION:** Q retains its default RAM capacity of two because setup changes only file capacity to 800 (`lib/PublishQueuePosixRK/src/PublishQueuePosixRK.h:58-71,399-415`; `src/Generalized-Core-Counter.cpp:647-653`).

**INFERENCE:** Hibernate is a useful model for bounded cloud/modem teardown, not for persistence step (2). In diagnostics builds, `flushDiagBatch()` can even enqueue a new RAM event after the queue gate and immediately before HIBERNATE.

## 5. Forced-flush availability and limits

**OBSERVATION:** Only S exposes a synchronous facade, `SystemConfig::flushNow() -> sysStatus.flush(true)` (`src/persist/SystemConfig.h:83-92`; `src/MyPersistentData.cpp:914-919`). C and N expose only deferred `loop()` methods (`src/persist/CurrentReadings.h:22-28`; `src/persist/SystemConfig.h:223-229`).

**OBSERVATION:** Adding matching C/N facades is four code lines at minimum: two declarations and two forwarding definitions beside `CurrentReadings::loop()` and `SensorSettings::loop()` (`src/MyPersistentData.cpp:1103-1108`; `src/persist/SystemConfig.h:223-253`).

**OBSERVATION:** Q already publicly exposes synchronous `writeQueueToFiles()` (`lib/PublishQueuePosixRK/src/PublishQueuePosixRK.h:231-234`).

**OBSERVATION:** Store writes truncate and rewrite 272, 36 and 88 bytes; the repository contains no measured write latency (`docs/work-orders/WO-2026-10-22-002-step0-report.md:81-87`).

**INFERENCE:** Initial bench acceptance limits should be: warning/enqueue 2 s; each store 250 ms; Q RAM-to-files 2 s; cloud disconnect 15 s; modem-off 30 s. Total worst case remains below the 60 s internal watchdog. These are provisional ceilings, not measurements.

**INFERENCE:** `flush(true)` is synchronous and has no cancellation hook (`lib/StorageHelperRK/src/StorageHelperRK.cpp:25-31,258-270`); a deadline can detect an overrun only after return. The hardware watchdog is therefore the actual bound on a stuck filesystem operation.

## 6. Error-state mechanics and recovery interactions

**OBSERVATION:** Error derives action solely from persisted alert plus reset count: 0 returns Idle, 2 soft-resets, 3 deep-powers-down; connectivity/sleep alerts may be suppressed in low-power modes (`src/state/State_Error.cpp:21-111,114-177`).

**OBSERVATION:** Error is entered from webhook escalation and two sleep-teardown failures; sleep-exhaustion’s post-reset transition is unreachable unless reset returns (`src/state/State_Report.cpp:136-150`; `src/state/SleepTeardown.cpp:192-212,313-330`; `src/state/State_Sleep.cpp:909-913`).

**INFERENCE:** A reset request must be separate from alert resolution: requested cause/action/deadline takes precedence, while ordinary alert-only Error entry retains today’s suppression policy.

**OBSERVATION:** Failsafe item 18 now treats Unknown openness as actionable and depends on persisted stage 2 surviving the reboot so that the later action is stage 3 (`src/power/ConnectivityFailsafe.cpp:227-255,301-314`).

**INFERENCE:** Central ownership must not clear or rewrite that ladder, and must preserve cause 2 for stage 2. The WO’s summarized item-24 durability gap is closed only if C/S/N/Q are persisted before that reset.

**OBSERVATION:** History contains no former common request owner to restore. Error ownership dates to the original state implementation; ThrashGuard has reset directly since its introduction, while OOM’s former Error route was intentionally removed (`src/state/State_Error.cpp:114-169`; `src/ThrashGuard.cpp:149-152`; `tests/oom_immediate_reset_test.sh:205-225`).

## 8. Behavioral risks, tests and bench plan

**OBSERVATION:** Cause values 1–7 are distinct, and startup plus device-status telemetry read `resetReasonData` (`src/ResetCause.h:5-23`; `src/Generalized-Core-Counter.cpp:1280-1294,1342-1376`; `src/cloud/DeviceStatusPublisher.cpp:525-529`).

**INFERENCE:** A single dynamic owner call must still pass the original requested cause, not generic cause 6. Deep power-down remains distinguished through the persisted failsafe stage/alert and reset reason, because it has no `System.reset(data)` payload.

**INFERENCE:** Do not route planned HIBERNATE through Error or alter `HibernateCycle::armForSleep()`; otherwise power-management wakes, retained hibernate classification and morning telemetry can regress (`src/state/State_Sleep.cpp:714-740`; `src/time/HibernateCycle.h:83-103`).

**OBSERVATION:** Tests requiring revision include `reset_cause_structural_test.py:38-43,89-132`, `oom_immediate_reset_test.sh:11-21`, `nightly_heap_guard_flush_test.sh:39-108`, sleep execution/plan transcript tests, connectivity-failsafe harnesses, and Error modem-teardown checks.

**INFERENCE:** Required new host mutations: drop each forced flush; swap every cause/action; bypass one owner request; stall each phase past deadline; reintroduce a direct reset/deep-power call; lose the two RAM Q entries; suppress OOM via alert policy; clear failsafe stage before reboot.

**INFERENCE:** Dev-14 bench: dirty all three stores and hold two RAM events; trigger connected and offline resets; verify files and queued events after reboot; verify each `resetReasonData`; force cloud-disconnect and modem-off timeout; inject OOM; exercise failsafe TEST_MODE stage 2→3 while observing modem rail/off-time; force the watchdog during teardown; then run two nightly hibernates and one OTA-in-progress case.

## 9. Recommendation

**STOP** the current whole-change WO. It exceeds +20, requires new phase state/timing, cannot make the vendored library’s fallback reset owner-compliant, and lacks safe semantics for OOM warning allocation and the watchdog backstop.

Recommend the small durability-only WO in **v49**: add C/N forced flushes and explicitly persist C/S/N/Q before failsafe stage 2/3. It closes the demonstrated loss without introducing the phased owner.

Recommend the full owner in **v50, after the native AM18x5 switch**, as separate ≤+20 WOs. Native `POWER_OFF` returns an error instead of privately calling `System.reset()`, removing the strongest ownership conflict (`docs/work-orders/WO-2026-10-31-001-step0-report.md:44,59-62,78-82`).

Before Stage 5, Chip/architect must rule: (1) watchdog resets are explicit owner exceptions; (2) OOM warning is best-effort and allocation-free failure proceeds immediately; (3) new RAM phase state/timer is authorized; and (4) “queue an alert” means a Q event or persisted `RecoveryState` alert code.
