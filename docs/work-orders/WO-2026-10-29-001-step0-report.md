## 2. Firmware and counting gap

**Observation:** the inspected legacy repo is `occ-mig/old-fw`, release `19.04`, product version `19` (`Occupancy-Sensors.cpp:47-51,103-105`); deployed devices actually run app versions `11`, `16`, `17`, or `19` (`evidence.md:7-19`).

- Debounce: legacy accepts `1–10 min` and repairs invalid persisted values to the `5 min` default (`Occupancy-Sensors.cpp:934-942,1198-1208`). GCC uses `sensor.setting1` in milliseconds; product `42131` supplies `300000 ms = 5 min` (`evidence.md:25`; `State_Modes.cpp:72-82,132-146`).
- Session credit: legacy adds rounded minutes at roughly `15 min` occupied updates and again when occupancy clears (`Occupancy-Sensors.cpp:177,747-750,759-765`). GCC accumulates exact seconds only when closing the session and displays integer minutes by truncating `/60` (`State_Common.h:361-395`; `PIRSensor.cpp:25-29`).
- Daily boundary: legacy clears occupancy at closing and resets daily state on the first open-hours loop of a new day (`Occupancy-Sensors.cpp:364,388-396,1052-1069,1287-1297`). GCC closes at the configured boundary, emits the closing report, then performs the daily reset (`State_Report.cpp:40-83,306-328`).
- Cadence: legacy reports state transitions, updates while occupied every `15 min`, and otherwise at hour changes (`Occupancy-Sensors.cpp:177,734-768,375-385`). Target mode `3` is `INTERMITTENT_KEEP_ALIVE`, so GCC reports transitions immediately but periodic occupancy only once per configured `3600 s` interval (`evidence.md:25`; `src/persist/SystemConfig.h:48-52`; `State_Common.h:45-58`; `State_Idle.cpp:189-218`).
- **Count direction:** during a live session, GCC `dailyoccupancy` will be lower/staler by the still-open session because it does not add legacy’s `15 min` chunks. At session end, GCC is within less than one displayed minute below exact elapsed time; legacy can differ either way by up to roughly half a minute per rounded credit operation, so no universal end-of-day direction is supportable (`Occupancy-Sensors.cpp:747-750,759-765`; `PIRSensor.cpp:27-29`).
- Known GCC exceptions are material: item `10` can add post-close activity to the next day (`RECOVERY_PLAN_2026-09-26.md:202-208`); item `19` observed a stuck-open `205 min` credit, about `108 min` too high (`RECOVERY_PLAN_2026-09-26.md:267-270`); item `15` can undercount the pre- or post-reset portion of one episode, inferred as up to about `2–3 h` (`RECOVERY_PLAN_2026-09-26.md:241-244`).
