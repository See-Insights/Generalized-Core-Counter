**Agents:** release PR, Claude Code itself (no model dispatch); soak grading, a **Sonnet subagent, medium** (needs S3, the Particle API and the forwarder). Report the model used.

## Plain goal

Move the firmware to Device OS 6.6.0 with **one variable changed**: v44 is v43's application code built for 6.6.0. **The OS move is one-way.** A device on 6.6.0 can't be put back on 6.4.1 over the air, so the rollout is bench first, then a few fleet devices, then the default.

## 1. Release PR (Claude Code)

- Branch `release/v44` from main. **Before building:** `git rev-parse HEAD:src` must equal v43's `src` tree (`71e346f`, `release/v43` `3328ee9`) except `FirmwareVersion.h`. If any Step 6 P-move has merged, branch from `71e346f` instead.
- `project.properties`: `deviceOS=6.6.0`. `bump_version.sh` to `v44-DeviceOS660` (or the nearest under the convention); product version 44. Final before the soak.
- CHANGELOG: "Device OS 6.4.1 → 6.6.0. No application change. Picks up the sleep-configuration leak fix we reported (forum 72797, PR #2968), cellular recovery and ledger fixes. One-way: devices can't return to 6.4.1 over the air."
- README and the `AI_DEVELOPMENT_WORKFLOW.md` toolchain paths (6.4.1 → 6.6.0), in the same PR.
- Fresh `BUILD_PATH_BASE` build on the 6.6.0 toolchain; `strings` shows the version; record the `.bin` size (Step 0 predicted 152726 B) and sha256; suite `N/N`.
- Report the keepalive environment-variable read (any `PARTICLE_*_KEEP_ALIVE` on the product or a device).
- Open the PR. **Don't merge until the bench soak passes**: main moves to 6.6.0 only then, and the P-moves build on 6.6.0 from that point.

## 2. Bench soak: Dev-09 and Dev-14, 48 h. Chip does the device steps

Chip uploads the PR's `.bin` as product v44 (size and sha256 must match the PR, §13 (j)), then OTAs it to **Dev-09 and Dev-14 only**, both locked, KEEP_ALIVE. Each is graded over 48 h from its first v44 boot, against its own v43 days (15–17 Oct).

**At the OTA (Dev-14):** record what the device downloads: system part(s), bootloader (3400?), softdevice or NCP, total bytes and time, from the Particle API events and serial.

**One step on Dev-09, about 24 h in:** Chip changes one harmless setting (e.g. `messaging.verboseTimeoutMin`). Pass: it lands at the next connection or boot, with no pin reset. That re-proves ledger delivery on 6.6.0, where the ledger code changed.

**Checks, per device:**
1. The v43 soak's checks (§2 of `2026-10-15-v43-release-and-soak.md`): payload unchanged, PIR and timer wakes, daily reset, standard checks. "Missing report" means one v43 would have sent (16 Oct ruling).
2. **Heap:** `fh` level across wakes. A steady per-wake fall is a FINDING (the leak fix should make no difference to us, so a fall would be new).
3. **Connection timing:** `connecttime` and `ConnSummary` `cellMs`/`cloudMs` against v43. The non-blocking handshake may shift `cloudMs`; report the medians, not a pass/fail.
4. **Modem teardown:** count `slow_teardown` latch trips, warm-to-cold steps in `connecttime`, and alert 15, against v43.
5. **Registration:** stalls and any long silences (the new registration backoff). Report the longest silence per device against v43.
6. **Watchdog:** any breadcrumb-28 watchdog is a FINDING and stops the rollout.

## 3. Fleet canaries (only if both bench devices pass)

Chip picks 2–3 production devices and locks them to v44 for 48 h. Architect's suggestion: **PCKL1** (the most informative: latch re-trips and sleep watchdogs) plus one device with a clean record. Grade them with the v42 health-check checks plus checks 2–6 above, against their own v43 days.

## 4. Default (only if the canaries pass)

Set v44 as the product default; merge the release PR; health check about 24 h later. Dev-09 and Dev-14 stay locked for the next soak (v45, the P-moves).

## Grading

PASS or FINDING per device, with log lines, ≤ 60 lines in chat; every number names its source and window. Results added to this file on a docs branch with a PR.
