## 2. Cases reasoned through

- **Untrusted or invalid time.** `signalLED` writes `ledOffTime = 0` when `!Time.isValid()`, and `signalLEDTimeRemaining()` returns 0 when `!Time.isValid()`: the new branch sees 0 and takes today's `min(debounceSeconds, wakeInSeconds)`. An untrusted-but-valid clock (item 18's reset case) uses the real deadline, which was set from the same clock. No change in the invalid case. The sleep-wake close itself is unchanged.
- **COUNTING LED.** The change is inside the OCCUPANCY branch only. The COUNTING defer (`:593–605`) and its sleep-wake close (`:1054`) are not touched.
- **Debounce expiring during a connect.** `handleOccupancyMode()` runs from the centralized sensor handling after every state-handler iteration, including Connect (`Generalized-Core-Counter.cpp:1224–1234`); it calls `updateOccupancyState()` (`State_Modes.cpp:116`), which closes on `millis() - lastOccupancyEvent > debounceMs` (`:127–160`). Unchanged. If the deadline passes while awake, the awake path closes the session and the device is no longer occupied at the sleep plan.
- **Reset mid-session.** `ledOffTime` is retained, so the remaining time survives the reset; `closeOccupancySessionSafely()` and the boot cap are untouched.
- **Expired-but-still-occupied at the plan** (remaining 0, occupied): falls back to today's full debounce, as the WO says. Not a regression. (If `signalLEDUpdate()` already cleared the LED while the session stayed open, the sleep-wake close cannot fire, because it needs `signalLEDStatus()`; that edge exists today and is outside this WO.)
- **A sleep that wakes a second early.** `remaining` would read 1, the plan sleeps 2 s, and the next wake closes; it converges and costs one short extra wake.
- **Clock stepped back while occupied** (not in the WO): `remaining` could exceed `debounceSeconds`; `min(remaining + 1, wakeInSeconds)` still bounds the sleep by the reporting boundary (the same as an ordinary timer wake), so the session closes no later than the next report. **Not capped; flagged for Stage 7 as Low.** I did not add a cap at `debounceSeconds`: it would defeat the WO's `remaining = 300 → 301` case and the `set1 = 0` case below.
- **`set1 == 0` mismatch (pre-existing):** the plan uses 60 s, while the LED is armed with `Config::occupancyDebounceMsForRuntime()` (`State_Modes.cpp:244–249`; the default is `DEFAULT_OCCUPANCY_DEBOUNCE_MS`). With `remaining > 0` the new code follows the real deadline, which is more correct; it is outside this WO to fix the fallback's 60.

## 3. The change as I would write it (about +7 net, plus a one-character fix)

In the occupied branch of `sleepPlan()`, after `debounceSeconds` is computed:
```
const uint32_t remaining = signalLEDTimeRemaining();   // 0 when expired or no valid time
if (remaining > 0) {
  const int untilDeadline = (int)remaining + 1;        // wake just after the deadline
  if (untilDeadline < wakeInSeconds) wakeInSeconds = untilDeadline;
} else if (debounceSeconds < (uint32_t)wakeInSeconds) {
  wakeInSeconds = (int)debounceSeconds;                // today's behavior, never worse
}
```
which replaces the existing 3-line `if (debounceSeconds < wakeInSeconds)` block (net +5 to +7 with comments), and in `logWakeSummary()` `(signalLEDTimeRemaining() / 1000UL)` becomes `signalLEDTimeRemaining()` (0 net). `remaining` and `untilDeadline` are new locals only: no new field, state, timer, schedule, alarm or config flag, so no §13 (c) STOP condition applies.
