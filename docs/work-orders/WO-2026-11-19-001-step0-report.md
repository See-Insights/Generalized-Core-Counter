# WO-2026-11-19-001 v2, Step 0 report (read-only)

Base `eb398b8`, source read from the extracted `src/` tree. Every `path:line` below is relative to `src/` and was opened. Run by Claude Code (model `claude-fable-5-2`), 19 Nov 2026. No source edited, no git run, no device or account changed.

## Verdicts

1. **`millis()` across ULP sleep: PASS.** Four bench measurements on Dev-09 and Dev-14 (Device OS 6.6.0, mode IKA) show device `millis()` advancing by the full sleep length, within 1 to 3 s of the Pi's wall clock, across ULP sleeps of 27 s to 10.5 min. A fifth check against the device's own RTC epoch agrees to under 1 s over 55 min. Particle's reference docs do not state this for `millis()` in so many words; the only explicit statement is a forum post by Particle's rickkas7. The bench data is the stronger evidence. No STOP.
2. **Readers: PASS for the four fields in `src/`, with two things to handle.** None of the four fields has a reader in `src/` outside the code the WO deletes. But two host tests and one test stub name them, so they must change in the same PR. `ENABLE_CONNECT_DECISION_TRACE` has other users (three blocks in `State_Connect.cpp` and the build-flags bit), so the flag itself must stay unless the architect widens the deletion.
3. **Row order: NEEDS RULING.** R1 does run before the already-connected check, and R1b is the `else` arm that closes the chain's enclosing `if`, at `:283-286`, after the chain, not before it. The WO says to keep R1b "before the call" and to move R1 into `decide()`. Those two instructions together change today's behaviour for a connected device with invalid config, and for the battery commit on the config-invalid path. One ruling on the call shape fixes it.
4. **The new field: PASS on the question asked, NEEDS RULING on one interaction.** `noteConnectTimeout()` has exactly one call site, the timeout path, and the stage-1 and stage-2 cloud recoveries do not pass through it. But `clearAtDailyClose()` zeroes the count before the decision runs on the daily-close report, so a hold at count 2 or more is cancelled at close. That contradicts the WO's answer 6 ("Daily close is held").

## Item 1 evidence: `millis()` across ULP sleep

**(a) Documentation.**
- `https://docs.particle.io/reference/device-os/api/sleep-sleep/ultra_low_power-systemsleepmode/` (ULTRA_LOW_POWER, Device OS 2.0.0 and later): "Real-time clock (RTC) is kept running." and "On wake, execution continues after the the `System.sleep()` command with all local and global variables intact." Neither sentence names `millis()`.
- `https://docs.particle.io/reference/device-os/api/time/millis/`: only the 49-day overflow; nothing about sleep.
- `https://community.particle.io/t/question-about-system-uptime/62436`, rickkas7, 13 Apr 2022: "On Gen 3 devices (Argon, Boron, B Series SoM, and Tracker), the millis() counter does increment during sleep." This is a forum reply, not the reference manual, and predates Device OS 6.x.
- Not verified: any Device OS 6.x release note on this. I did not find one.

**Limits of this evidence.**
- The `Sleep: ULP ... dur=Ns` and `WakeReturn: elapsed=...` lines never reach the archive: USB drops before the forwarder reads them. So no measurement pairs a logged `dur=` with a millis difference. The Pi clock stands in for it.
- All four are USB-powered bench boards with standby requested but not effective (`standby=1/0`). Not verified on a battery-only field board, though the timer source is the same.
- The WO's quoted lines "Serial, 23:48–23:49Z" (`Sleep: ULP standby=0 reason=debounce dur=70s occ=1`, `INV: awake_ms=6513806`) are not in the S3 archive: Dev-09's last serial object on 18 Nov is `23-46-45`, and 19 Nov has none. Not verified from this source.

**How the firmware assumes it.** `state/State_Sleep.cpp:805` takes `millis()` before `System.sleep()` (`:811`) and `:813` computes `sleepElapsedMs = millis() - sleepCallStartMs`, logged as `WakeReturn: elapsed=` (`:951-953`). The `SLEEP_PREP elapsed=330978` line in example 1 is the same assumption holding in practice.

**Wrap.** `millis()` wraps at about 49.7 days; unsigned subtraction handles one wrap, and the hold is 6 h at most. The count and the stamp are both RAM, so a hibernate wake or reset clears both together.

## Item 3 evidence: order in `handleReportingState()` (`state/State_Report.cpp:32-297`)

1. `:33-35` log the state entry. `:37-43` read `now` and the daily-close test (`due`).
2. `:45-62` when `due`: log, and close an open occupancy session.
3. `:67-70` measure, read battery, `publishData()` (the report is queued here, before any decision).
4. `:74-75` take and clear `occupancyChangeTriggered`.
5. `:77-88` when `due`: `dailyCleanup()`, re-open a straddling session, and **`clearAtDailyClose()` at `:87`**.
6. `:92` stamp `lastReport`. `:96-98` reset hourly totals in COUNTING.
7. `:112-156` webhook supervision: may raise alert 40 (`:126`), set `forceConnectForLongTermWebhook` (`:133`), or **exit 1: R0**, ERROR_STATE and `return` (`:150-151`).
8. `:162-165` take and clear `serviceRequestTriggered`.
9. **Exit 2: R1**, `:167-170`: config invalid goes to CONNECTING and returns. This is before the connected test, so it fires whether or not the cloud is connected, and it skips steps 10 to 12.
10. `:173` `if (!Particle.connected())` opens. Inside it: `:174-176` resolve the reporting policy (this fixes `cadenceDue`, before the commit); `:184-192` battery commit; `:199-207` the 30 s defer; `:211-216` `returnToSleepAfterReport`.
11. `:220-282` the chain: R2 `:220-225`, R3 `:226-231`, R4 `:232-234`, R5 `:235-239`, R6/R7 `:240-252` (reads the effective mode after the commit), R8/R9 `:253-267`, R10 `:268-282`.
12. **R1b**, `:283-286`: the `else` of `:173`. It runs only when connected and config is valid; it stamps `lastConnection` and goes to IDLE.
13. `:294-296` a log line when alert 40 is active. No `return` after the chain.

There are only two early exits, R0 and R1, and both are named in the WO. No unnamed early exit was found.

**Where the WO and today's order disagree.**
- **R1b is not "before the call" today.** It is checked at `:173`, after R1. If the new code tests "connected" first and calls `decide()` only when not connected, a connected device with invalid config goes to IDLE `already connected` instead of CONNECTING `config invalid`. Today that path re-enters CONNECTING, which sees the cloud already up and reloads config (`state/State_Connect.cpp:446`, `:536`).
- **The battery commit and `returnToSleepAfterReport` are inside the not-connected branch and after R1.** The WO lists them as "keep before the call". If they run before a `decide()` that includes `configInvalid`, the config-invalid path gains a battery commit and may gain `returnToSleepAfterReport = true`, which sends its successful connect to Sleep (`state/State_Connect.cpp:598-601`) instead of IDLE.
- **An order-preserving shape:** test `configInvalid` at today's position and ask `decide()` with it (so the hold can still apply); otherwise, if connected, take R1b; otherwise commit, set the flag, and ask `decide()` with the other triggers. Whether the hold applies to a connected device with invalid config is part of the same ruling.

## Item 4 evidence: where the failure is counted

- **One call site.** `noteConnectTimeout()` is defined at `power/ModemHealth.cpp:55-63` and called only at `state/State_Connect.cpp:641`, inside `if (elapsedMs > budgetMs)` (`:608-655`). Setting `lastConnectFailMs` beside it puts the stamp on the timeout path and nowhere else.
- **S15/S16 do not pass through it.** Stage 1 (`requestCloudAcquireStage1Recovery()`, `state/State_Connect.cpp:90-93`) and stage 2 (`:95-104`) are called from `:382-405`, guarded by `state == CONNECTING_STATE && connectRequested && !cloudConnected` and the CLOUD_ACQUIRE phase (`:379-380`). They set local statics and call `Particle.connect()`; they do not transition, do not touch `session.modemConnectTimeoutCount`, and do not reset `connectionStartTimeStamp` (set once on entry, `:232`). The attempt keeps the same budget and ends at success (`:446-605`) or at the one timeout (`:608`). `CloudRecover: exhausted` (`:612-617`) is only a log inside the timeout path.
- **The count is cleared in three places, not one.** `noteConnectSuccess()` (`power/ModemHealth.cpp:65-69`, from `state/State_Connect.cpp:590`); `maybeClearModemUnstable()` (`power/ModemHealth.cpp:47`, needs this wake cycle's connect result to be SUCCESS, so it follows a success); and `clearAtDailyClose()` (`power/ModemHealth.cpp:71-79`, zeroes the count at `:76` only when `modemUnstable` is set).

**Other exits from CONNECTING that are not timeouts.** None sets the count or would set the field.

| Exit | Line | What happens | Counted? |
|---|---|---|---|
| User switch, from any state | `Generalized-Core-Counter.cpp:1188-1192` | REPORTING `user switch`; the attempt is abandoned, then restarts as `service request` with a fresh budget | No (and exempt from the hold) |
| ThrashGuard tier 2 | `ThrashGuard.cpp:139-146` | Alert 18, radio off, Sleep `thrash tier 2` | No |
| ThrashGuard tier 3 | `ThrashGuard.cpp:149-153` | Reset | No; RAM lost |
| Connectivity failsafe stage 2 / 3 | `power/ConnectivityFailsafe.cpp:313-331` | Reset or power-off; deferred while an attempt is inside its budget (`:289-291`) | No; RAM lost |
| Out of memory | `Generalized-Core-Counter.cpp:1181-1184` | Reset | No; RAM lost |
| App watchdog | `observability/LoopForensics.cpp:396-398` | Reset | No; RAM lost |
| Updates pending (X1) | `state/State_Connect.cpp:596-597` | FIRMWARE_UPDATE, after `noteConnectSuccess()` | Success, not a failure |

- ThrashGuard's CONNECTING limit is 120 s (`ThrashGuard.cpp:63-64`), but CONNECTING marks progress every 30 s while inside its budget (`state/State_Connect.cpp:411-415`), so tier 2 during a normal attempt is unlikely. It is still an uncounted failure exit.
- There is no error, cancel, mode-change or config-change exit: CONNECTING checks nothing but the cloud and the budget (map row C6).
- A cloud connect that succeeds and then loses the link (Dev-09: `Connect: ok elapsed=351487ms` then `PPP link failed: error 5`) counts as a success and clears the hold.
- The timeout path serves every entry to CONNECTING, including the bypass sites S1 to S6. A failed boot or `sleep-open-hours-reconnect` attempt will therefore start a hold for REPORTING too.

## For the architect to decide

1. **Call shape and order (item 3).** Should a connected device with invalid config still go to CONNECTING `config invalid` as today, and should the config-invalid path keep skipping the battery commit and `returnToSleepAfterReport`? The order-preserving shape above does both.
2. **Daily close and the hold (item 4).** `clearAtDailyClose()` at `state/State_Report.cpp:87` runs before the decision and zeroes the count when `modemUnstable` is set (count 2 or more, or a slow teardown). So the daily-close report escapes the hold in exactly the worst cases, and is held only at count 1 with a stable modem. Dev-09 shows the path: `Connect: fail` at 14:10:30Z, `Sleep->Report reason=close due before night sleep`, `Connect: start` at 14:10:54Z. Either accept one close attempt per night, or stop `clearAtDailyClose()` from zeroing the count. The host test "closeDue gives WAIT inside the hold" will pass either way, because it cannot see this.
3. **The trace flag (item 2).** Keep `ENABLE_CONNECT_DECISION_TRACE` for the three `State_Connect.cpp` blocks and the `0x0040` build-flags bit, or delete those too. Deleting the bit changes a reported status field.
4. **Tests that name the deleted fields (item 2).** Confirm the two tests and the stub are in scope for Stage 6, and that changing the equivalence test's dump is acceptable.
5. **Uncounted failure exits (item 4).** ThrashGuard tier 2 leaves CONNECTING with the radio off and no count. Leave as is (rare), or stamp it as a failure.
6. **Bypass sites feed the hold (item 4).** Confirm that a timeout from S1 to S6 should hold the REPORTING path. Step 1 does this without being asked.
7. **Bench expectation.** On Dev-09 the back-to-back loop is `Connect->Sleep reason=connect-timeout`, then `Sleep->Report reason=occupancy change pending`, then `Report->Connect reason=occupancy change`, all within about 300 ms of device millis. With the hold, the second step still happens (and queues a report) each time occupancy changes; only the third becomes `connect hold`.
