# WO-2026-10-09-003 Step 0: the modem standby latch

**Base:** `5c56e07` on `wo/2026-10-09-003-standby-latch` · **Date:** 2026-10-09 · **Model used:** claude-sonnet-5-5, reasoning: high (set by `--effort high`)

**Plain goal:** a device whose standby was suppressed after a slow teardown gets standby back without a reboot, unless its modem is genuinely still failing.

**Verdict: PROCEED with option (b), about +8 `src/` lines in `State_Report.cpp`.** One caution up front: a standby teardown never exercises the modem, so the dispatch's "retry and let the check re-trip" cannot detect a failing modem during open hours (§3).

## 3. Smallest recovery that keeps the protection

**The key fact.** Under standby the teardown is cloud-only. Its budget is the cloud budget capped at 5 s (`State_Sleep.cpp:754-758`; `ConnectivityPolicy.h:199`). Logged cloud times are 16–60 ms. So the 10 s check (`:887`) cannot trip on a standby teardown, and it says nothing about whether the modem powers off. The modem-off check runs only on full modem-offs: the closed-hours night teardown, a forced modem-off, and the connect-timeout teardown. (OBS: code and logs.)

|---|---|---|---|
| **(a) Retry after N clean cycles** | about +11: one `session` counter in `StateMachine.h`, about 10 in `State_Sleep.cpp`, around `:129-148` and `:887-891` | The standby teardown's own time. That is cloud-only, so it passes almost always. | Medium. Standby returns intraday, within N cycles, but the retry cannot see a bad modem. A failed retry shows up only through the 5 s budget (`:836`: alert 15, ERROR_STATE, re-trip) or two connect timeouts, each costing up to 660 s of awake time. The counter is RAM-only and allowed. |
| **(b) Clear once per day at the close** | **+8 in `State_Report.cpp`, no new field** | The night full modem-off, already measured by `:887`. If the modem is still slow it re-trips that night; if healthy, standby is back the next morning. | Low. No open-hours exposure before a verdict exists. Latency is up to about a day. An always-slow modem such as Dev-09's 9–22 s re-trips every night, so for it nothing changes. That is by design, but it is a policy call (Open point 1). |
| (c) Judge recovery on cloud-disconnect time | +2 | The cloud time, 16–60 ms | High. It clears at the first clean cycle, and nothing downstream can re-trip it. |
| (d) Close the 5–10 s dead band (recovery threshold 5 s to 10 s) | +1 (constant `:32`) | Same as today | Low. It helps only 5–10 s modems, and the threshold sits on the trip boundary. It could be added to (b) if Chip wants. |

**Pick (b).** It reuses the existing once-per-day signal: `due` from `DailyBoundary::check` (`State_Report.cpp:39-42`). The same block stamps `set_lastDailyCleanup(now)` at `:82`, so a clear placed there runs once per day. It adds no persisted field, timer or schedule.

Proposed insertion, after `:82` inside `if (due)`:
```
if (session.modemUnstable) {
  session.modemUnstable = false; session.modemUnstableReason = 0;
  session.modemConnectTimeoutCount = 0; session.modemStandbySuppressed = false;
  Log.info("MODEM_POLICY: standby re-allowed at daily close; night modem-off decides");
}
```
- **Why at the close, not the open hour:** the night full modem-off falls after the close and acts as the verdict. An open-hour clear would have no verdict before the first standby sleep. The close clear is also the only option with an existing day-boundary signal, which satisfies the no-new-state rule.
- **Untrusted clock:** `due` is false (`DailyBoundary.h:20-22`), so nothing clears and today's behaviour applies.
- **Coverage gap:** if the night has no modem-off to measure (the radio is already off after a connect timeout), standby returns without a verdict. The connect-timeout path (two timeouts) is then the only re-protection (INF).
- **Hibernating devices:** a hibernate wake resets RAM (`State_Sleep.cpp:1124-1170`), so the latch already ends there. Per the fleet notes only Trail02 has hibernate enabled. (INF)

*Appended by Claude Code, 2026-10-09 (fleet evidence; read-only Particle API and S3 status events):*
- **Open point 2, answered: the bench devices hibernate nightly.**
  - Dev-09's and Dev-14's `device-settings` have `modes.enableHibernateSleep: true`.
  - Their status events show `sleepMode: hibernate`. For example, Dev-09 on 2026-10-08 at 22:01Z: `resetReason 30`, `wakeReason DEEP_POWER_DOWN`, `hibernateCount 9`.
  - A hibernate wake resets RAM, so **on these two devices the latch already ends each night.** The 8 and 9 Oct latches lasted the rest of each day: 12:19 SGT to close on 8 Oct, and 13:49 to the 14:26 pin reset on 9 Oct.
- **The US fleet does not hibernate.**
  - The product `default-settings.modes` has no `enableHibernateSleep`, and the firmware default is false (`MyPersistentData.cpp:153`).
  - S3 status events from 1–9 Oct for Court1–3, PCKL1–3 and MAFC-1/2 show no `sleepMode: hibernate`. Trail02 is set to hibernate, but its v38 status carries no `sleepMode` field.
  - **On US devices a latch would persist until the next reboot, possibly for days,** forcing a cold registration on every KEEP_ALIVE reconnect in open hours. Option (b) mainly helps these devices.
- **Trip and recovery counts from the forwarder are not yet gathered.** The AWS SSO token expired mid-query, so queries returned errors, not zero lines. Only Dev-09 and Dev-14 forward serial, so US devices' latch state is unobservable.
