## 2. Is stored configuration a redundant cache?

**Observation.** Current boot loads the three files before using persisted configuration, marks it STORAGE only when `hasValidLedgerConfig` is true, and does not call ledger `.get()`/apply until connected (`src/Generalized-Core-Counter.cpp:493-505,528-532`; `src/state/State_Connect.cpp:534-548`; `src/cloud/Cloud.cpp:634-644`). Thus the present offline boot uses the StorageHelperRK cache, not a local-ledger read.

**Observation.** Whether Device OS 6.6.0 `.get()` returns the last synced ledger contents before connection **cannot tell** from this tree; only the target OS is pinned here (`project.properties:3-4`). Bench test: sync distinctive values, disconnect, then offline reboot and full power cycle; call/read both ledger `.get()` values before `Particle.connect()`, apply them, and verify timezone, hours, modes, sensor settings, webhook, and thermal thresholds.

**Observation.** On a never-synced device, empty ledgers make every absent section return success; after the timeout, “neither synced” is accepted, compiled defaults validate, and `markLedgerConfigurationValid()` sets `hasValidLedgerConfig=true` (`src/cloud/ConfigApply.cpp:181-189,232-240,332-340,410-418,533-540,597-609`; `src/cloud/LedgerClient.cpp:234-247`; `src/cloud/Cloud.cpp:597-619`; `src/Config.cpp:154-160`). Therefore that flag proves a valid resulting configuration, not that cloud content was ever received.

**Inference.** If the bench proves pre-connection local-ledger replay, all class-(a) fields—22 SysData fields and five SensorData fields, totaling 160 B—are redundant as authoritative storage; the table identifies them and the ledger apply paths already cover them (`src/cloud/ConfigApply.cpp:122-148,181-674`).

## 3. Wrong-to-persist fields

**Observation.** `lastOccupancyEvent` is the sole class-(e) field: subtracting a previous boot’s `millis()` from the new boot’s value can wrap and immediately satisfy the debounce test (`src/state/State_Idle.cpp:51-61`; `src/state/State_Modes.cpp:132-144`). Current code prevents that behavior by clearing it immediately after loading and rearming zero from this boot (`src/Generalized-Core-Counter.cpp:497-505`; `src/state/State_Idle.cpp:51-55`).

**Inference.** Recovery-plan item 15 is separate: `occupied`, `occupancyStartTime`, and `totalOccupiedSeconds` correctly need persistence, while the boot anchor caps the first post-reset close at the boot epoch and at `anchor+debounce` (`src/state/State_Common.h:350-360`). Field evidence shows possible 2–3-hour episode loss but remains unresolved; it does not justify persisting `lastOccupancyEvent` (`docs/RECOVERY_PLAN_2026-09-26.md:232-235`).

## 4. Storage mechanics

**Observation.** A version mismatch fails validation; `load()` then zeroes and initializes the entire record, so a bump loses every field in that file (`lib/StorageHelperRK/src/StorageHelperRK.cpp:112-156,228-252`). An older firmware reading a newer/larger same-version file reads only its smaller buffer; the newer header’s `size > dataSize` fails validation, and the old record is initialized and later saved with truncation—also whole-record loss (`lib/StorageHelperRK/src/StorageHelperRK.cpp:122-141,234-252,258-270`).

**Observation.** Changed values alone schedule writes; SysData coalesces until 100 ms quiet, SensorData and CurrentData until 250 ms quiet, while ledger-valid and failsafe paths force SysData immediately (`lib/StorageHelperRK/src/StorageHelperRK.h:692-706`; `src/MyPersistentData.cpp:76-87,577-586,678-687`; `src/Config.cpp:154-160`; `src/power/ConnectivityFailsafe.cpp:135-149`). Each save truncates and rewrites the full logical file—272, 36, or 88 B—so event rate determines write count; physical erase/write amplification **cannot tell** from this tree (`lib/StorageHelperRK/src/StorageHelperRK.cpp:258-270`).

**Observation.** Each additional file costs at least a 16-B RAM/file header plus payload/padding, one RAM record buffer, a filesystem object, and one open/read/hash validation at boot; exact allocator overhead, flash allocation units, and boot latency **cannot tell** without a build and timed bench (`lib/StorageHelperRK/src/StorageHelperRK.h:565-585,920-973`; `lib/StorageHelperRK/src/StorageHelperRK.cpp:228-252`).

## 5. Target shape

| Shape | Net `src` lines; risk; downgrade |
|---|---|
| A: unchanged layout, dead accessors removed | At most −127 code SLOC: 120 dead-accessor SLOC plus seven dead init/write calls, derived from Q1’s accessor ranges and writers. No data migration; v45-safe because bytes, sizes, magic, and versions remain unchanged (`src/MyPersistentData.h:117-193,677-697`). |
| B: four new files plus migration | At least +148 code SLOC during coexistence: four × the 37 non-comment lifecycle lines used by the smallest existing store, before accessors or migration (`src/MyPersistentData.cpp:559-609`). High migration risk; downgrade requires dual-writing every state change because otherwise v45 sees stale legacy state, while changing a legacy size/version makes v45 initialize it (`lib/StorageHelperRK/src/StorageHelperRK.cpp:122-156`). |
| C: no stored config | Boot replay can reuse the existing 11-line loader and should be capped at +20, but exact net lines **cannot tell** until the Device OS bench and RAM-holder design exist (`src/cloud/Cloud.cpp:634-644`). Stopping the legacy mirror immediately is downgrade-unsafe after a ledger change because v45 would boot its stale file (`src/Config.cpp:162-169`). |

**Inference.** Recommend **A plus freeze-and-extend**: preserve the three v45 records forever as compatibility records, remove dead plumbing, never append another field, keep mirroring existing class-(a) values while v45 rollback is supported, and place only future persistent fields in a file owned by their concern. New config fields remain ledger/RAM-only after the offline-ledger bench. This avoids migration, reduces lines, and makes a new field touch one concern (`src/persist/SystemConfig.h:7-18`; `src/persist/RecoveryState.h:7-16`; `src/persist/CurrentReadings.h:4-14`).

## 6. Fleet path

**Observation.** If no valid GCC records exist, first GCC boot initializes the three records; counts and occupancy totals initialize to zero, while configuration gets compiled defaults until ledger apply (`src/MyPersistentData.cpp:123-164,596-609,689-777`). The accepted fleet cutover is the first connection after opening so the update day is wholly GCC (`c52b6bc:docs/work-orders/WO-2026-10-20-004-fleet-convergence-step0.md:61-68`).

**Inference.** No count seeding is required if that cutover invariant is enforced. If any legacy pulses occur after opening but before the OTA reboot, hourly/daily counts must instead be seeded or those pulses are lost; the recommended frozen layout neither adds nor removes that operational requirement (`src/MyPersistentData.cpp:699-707`; `src/state/State_Modes.cpp:26-42`).
