## 4. The smallest fix

**Rule:** in INTERMITTENT, when the effective cadence is at least 3 h, the stale threshold becomes cadence + 3 h. That is 3 h past a missed due connection. Otherwise it stays 3 h.

Sketch, placed after `Main:2626` (so there is no per-loop cost):
```
if (PowerManager::instance().effectiveConnectionMode() == SystemConfig::INTERMITTENT) {
  const time_t cadenceSec = (time_t)ReportingPolicyResolver::resolveRuntime(
      PowerManager::instance().soc(), now).effectiveIntervalSec;
  if (cadenceSec >= STALE_SEC && connectionAgeSec < STALE_SEC + cadenceSec) return;
}
```

Estimate: **about +13** against the ≤+20 target. It uses only existing state (`resolveRuntime()`, `effectiveIntervalSec`); no new field.

| Path | Effect |
|---|---|
| CRITICAL (4 h), or an interval over 3 h, in INTERMITTENT | Delayed: reset at 7 h, not 3 h. This is the spurious path being removed. |
| HEALTHY or CONSERVING INTERMITTENT (≤ 2 h, below 3 h) | Unchanged: a failing device resets at about 3 open hours (v32). |
| KEEP_ALIVE and CONNECTED | Unchanged. |
| SURVIVAL on battery | Unchanged: it is still blocked at `:2664`. |

A genuinely failing device on a short cadence still escalates on the v32 schedule. On a long cadence it escalates 3 h after its first missed due connection.

- **Hibernate wake alignment** with 4 h boundaries was not traced. The fix does not depend on it.

## 3. Cadence rule without the INTERMITTENT condition

- **Re-estimate:** about 3 code lines and 2 comment lines. With a test-mode guard, about **+7** in `Main`.

- **On the fix's path: YES, at the input.** `ConfigApply.cpp:265` accepts 65536–86400 s and `:267` wraps it into the `uint16_t` store. For example, 86400 becomes 20864 s.
- The fix's own read (`effectiveIntervalSec`) is not truncated and the product cannot overflow. It reads the wrapped stored value, which is also what the cadence logic uses, so the fix stays self-consistent. Its threshold would be cadence + 3 h for 20864 s, not for 86400 s.
- **Remedy:** cap the range at 65535 on `ConfigApply.cpp:265` (0 net lines). That rejects 65536–86400 configs, so it needs the architect's ruling.
- **Outside the path (for the recovery plan):**
  - `ConfigApply.cpp:266`: `uint16_t` is compared with `int`, so a wrapped value never matches and rewrites on every config apply (INF).
  - `State_Idle.cpp:144,196` and `State_Sleep.cpp:1054,1790` hold `uint16_t intervalSec`. No loss, since the source is `uint16_t`.

## 5. Flash churn (for the recovery plan, as written)

- At stage 0 the cooldown test (`Main:2651`, `currentStage != 0 && ...`) is false, so a low-battery block (`:2661-2664`) reaches `persistConnectivityFailsafeState(currentStage, now, false)` (`:2674`) on **every loop pass**.
- That call sets the last action to `now` and then runs `SystemConfig::flushNow()` (`:404-413`). `flushNow` is `flush(true)` (`MyPersistentData.cpp:1003`), which saves the file when dirty (`StorageHelperRK.cpp:25-31`).
- The store is a flash file (`PersistentDataFile`, `MyPersistentData.cpp:69`).
- `setValue` marks it dirty only on change (`StorageHelperRK.h:700-702`). `now` changes once per second, so the bound is about one flash write per second while the block keeps firing: age ≥ 3 h, Open, no connect in budget, battery with a downgrade or SURVIVAL, stage 0.
- At stage ≥ 1 the 6 h cooldown limits it.
- I did not measure wear or how long the loop stays awake (INF).
