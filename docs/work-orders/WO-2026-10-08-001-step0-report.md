## 4. The smallest fix

**Rule:** in INTERMITTENT, when the effective cadence is at least 3 h, the stale threshold becomes cadence + 3 h. That is 3 h past a missed due connection. Otherwise it stays 3 h.

Sketch, placed after `Main:2626` (so there is no per-loop cost):
```
if (PowerManager::instance().effectiveConnectionMode() == SystemConfig::INTERMITTENT) {
  const time_t cadenceSec = (time_t)ReportingPolicyResolver::resolveRuntime(
      PowerManager::instance().soc(), now).effectiveIntervalSec;
  if (cadenceSec >= STALE_SEC && connectionAgeSec < STALE_SEC + cadenceSec) return;
}
```

Estimate: **about +13** against the ≤+20 target. It uses only existing state (`resolveRuntime()`, `effectiveIntervalSec`); no new field.

| Path | Effect |
|---|---|
| CRITICAL (4 h), or an interval over 3 h, in INTERMITTENT | Delayed: reset at 7 h, not 3 h. This is the spurious path being removed. |
| HEALTHY or CONSERVING INTERMITTENT (≤ 2 h, below 3 h) | Unchanged: a failing device resets at about 3 open hours (v32). |
| KEEP_ALIVE and CONNECTED | Unchanged. |
| SURVIVAL on battery | Unchanged: it is still blocked at `:2664`. |

A genuinely failing device on a short cadence still escalates on the v32 schedule. On a long cadence it escalates 3 h after its first missed due connection.

## Open points

- **Fleet impact is unverified.** No device is known to be at CRITICAL in INTERMITTENT, or to be configured above 3 h. Court3's 140/2 resets on v36 may be real outages. The ledger or config values are not in the repo.
- **Possible larger gap (INF).** `lastConnection` is written only at `State_Connect.cpp:513`. `State_Report.cpp:168,279` skips CONNECTING when `Particle.connected()` is already true. A device that stays on the cloud in CONNECTED or KEEP_ALIVE might never refresh it, and so age past 3 h. I did not trace this. It needs logs and its own check; this fix does not cover it.
- **Flash churn (INF).** When the `:2661` block triggers at stage 0, the cooldown at `:2651` does not apply, so `persistConnectivityFailsafeState(...)` (`:2674`, `flushNow` at `:413`) may run on every loop pass. I did not measure it.
- **`uint16_t` truncation (INF).** `Config.h:69` returns `uint16_t`, but `ConfigApply.cpp:265` accepts up to 86400 s. I did not assess it.
- **Hibernate wake alignment** with 4 h boundaries was not traced. The fix does not depend on it.
